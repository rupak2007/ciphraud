## 1. Class imbalance

- **Global fraud rate: 3.499%** (20,663 positive / 590,540 total) — matches the publicly documented
  rate for this dataset and confirms the file wasn't corrupted or subsampled.
- Fraud rate is **not stable over time**: across 182 daily buckets it ranges from **1.10% to 6.99%**
  (mean 3.60%), visibly more volatile after day ~60 (`results/phase1_eda/fraud_rate_over_time.png`).
- **Implication**: any fixed train/val/test split must be checked for per-fold positive *counts*, not
  just rates — a fold landing in a low-rate period could leave too few positives to evaluate
  precision/recall meaningfully.

## 2. `TransactionDT` semantics — confirmed a delta, not a timestamp

All checks were designed to be falsifiable; none were assumed.

| Check | Result | Interpretation |
|---|---|---|
| `min` value | 86,400 | A Unix epoch would be ~1.5×10⁹ — this is ~1 day. Epoch reading is **implausible**. |
| `max − min` | 15,724,731 s | Interpreted as seconds: **182.0 days**. As an epoch-seconds span: ~48 years. Only the former is a plausible dataset window. |
| Hour-of-day histogram | Clear diurnal cycle, **trough at hour 9**, relative amplitude 1.61 (`hour_of_day_histogram.png`) | A real e-commerce traffic pattern exists only if the unit is seconds. This is the strongest evidence. |
| `Spearman(TransactionID, TransactionDT)` | **0.99999999999974** | `TransactionID` is essentially a perfect time-order proxy. |
| Monotonicity | Non-decreasing across the whole file | The file ships pre-sorted by time. |
| Adjacent duplicate `DT` values | 17,191 | Real ties exist; a split boundary must not fall inside a tied block. |
| Max gap between consecutive values | 4,138 s (~69 min) | No extreme collection outage. |

**Conclusion**: `TransactionDT` is a relative offset in seconds from an unknown, unrecoverable
reference point, spanning ~182 days. The absolute calendar date is unknown and unknowable from this
data alone — that unrecoverability *is* the delta claim, not an assumption.

**Consequence for modeling**: because `TransactionID` is a near-perfect proxy for `TransactionDT`
(ρ≈1), **`TransactionID` must never be used as a model feature** — it would functionally leak
temporal order (and by extension, the drift documented below) straight into the model.

## 3. Missingness — global rate hides a critical time-drift trap

- No column is 100% missing (max is `dist2` at 93.6%); 20 of 394 columns are complete.
- By family, mean missing rate: `D` 58.2%, `dist` 76.6%, `M` 49.9%, `email` 46.4%, `V` 43.0%, `addr`
  11.1%, `card` 0.5%, `C`/`core` 0%.
- **Critical finding — feature-availability drift**: comparing the first 20% of days against the
  last 20% of days, a specific block of columns (`M7`, `M8`, `M9`, and a V/D block including `V1–V11`
  and `D11`) goes from **~69–84% missing early** to **~28–39% missing late** — a swing of over 40
  percentage points. Their *global* missing rate (47–59%) looks like unremarkable moderate
  missingness and completely hides this. These columns became far more available partway through
  the collection window (likely an upstream instrumentation change).
- **Implication for Phase 2**: any global-fill imputation (e.g., "fill with the training-set mean")
  is unsafe for this block — it would implicitly leak the fact that late-period rows are more likely
  to have this data. Imputation and any "missingness indicator" features must be computed within the
  past-only scope of whatever split window they're used in, and this specific column block deserves
  explicit review before Phase 2 finalizes its strategy.

## 4. The 339 anonymized `V` columns — structural grouping via null-mask identity

With no data dictionary for `V1`–`V339`, missingness *pattern* is the only available structural
signal. Grouping columns by **exact identical null mask** (not correlation — see §7 for why)
collapses the 339 columns into **exactly 15 blocks**, no singletons, sizes ranging from 11 to 46
columns (`results/phase1_eda/v_null_mask_blocks.csv`). This strongly suggests the V columns are
aggregated features computed by ~15 distinct upstream feature-generation processes, each applied
uniformly to whichever rows had the necessary source data.

**Implication for Phase 4**: these 15 blocks are a natural unit for feature-tier construction —
e.g., sampling representatively across blocks, rather than by column-index proximity, avoids
accidentally dropping an entire upstream signal source at a small feature-count tier.

## 5. Numeric ranges — the FHE quantization risk surface

- **`TransactionAmt`**: min \$0.251, max \$31,937.39, mean \$135.03, median \$68.77, **skew 14.37** —
  heavily right-tailed. This is the clearest example of why low-bit (4–8 bit) quantization
  (Phase 5) is nontrivial: a linear quantization grid sized to the max would waste nearly all
  resolution on the dense sub-\$200 region where most transactions live.
- Several `V` columns are far more extreme: e.g. `V305` has skew 384 (a near-constant column with a
  single rare outlier), and `V311`/`V129`/`V309`/`V206`/`V319` have max values in the 55,000–104,000
  range against means under 20 — i.e., a rare extreme spike sitting on an otherwise near-zero column.
- Full per-column min/max/mean/std/skew/quartiles: `results/phase1_eda/numeric_ranges.csv` (378
  numeric columns measured; the other 16 are the 14 low-cardinality categoricals + `TransactionID` +
  `isFraud`).
- **Implication for Phase 5**: quantization calibration should not naively use raw min/max for these
  heavy-tailed columns — expect this to force either clipping/winsorization or a
  non-uniform quantization scheme, and expect this to disproportionately affect a small number of
  outlier-heavy `V` columns rather than the dataset broadly.

## 6. Categorical cardinality and out-of-vocabulary risk

- 14 columns were inferred as low-cardinality categoricals: `ProductCD` (5), `card4` (4), `card6`
  (4), `M1`–`M9` (2–3 each), `P_emaildomain` (59), `R_emaildomain` (60).
- **OOV rate at every one of the 3 candidate split boundaries, for every one of these 14 columns, is
  exactly 0.0%** (`results/phase1_eda/oov_rates.csv`) — every value seen in a later window already
  appeared in the preceding window. These vocabularies are effectively closed and small.
- **Scope note**: `card1`, `card2`, `card3`, `card5` are numeric-typed card-identifier codes, not
  analyzed here as categoricals (they were inferred as numeric during loading) — they are
  high-cardinality identifier-like columns and need explicit encoding-strategy attention in Phase 2
  despite their numeric dtype. Similarly, the identity table's `DeviceInfo` (free-text device
  strings) and `id_12`–`id_38` were **not** cardinality/OOV-profiled in Phase 1 — this analysis was
  scoped to `train_transaction.csv`'s own columns; profiling the identity table's categoricals is
  deferred to Phase 2 alongside the actual join.
- **Implication for Phase 2**: past-scoped frequency encoding is safe and low-risk for the 14
  profiled categoricals. `card1`/`card2`/`card3`/`card5` and the identity-table categoricals need
  their own cardinality/OOV check before Phase 2 commits to an encoding strategy for them.

## 7. Identity table coverage

- Only **24.42%** of transactions have a matching identity row (144,233 of 590,540).
- Coverage is **not independent of the label**: 54.77% of fraudulent transactions have identity data,
  versus 23.32% of legitimate ones — fraud transactions are **more than twice as likely** to carry
  identity information.
- This is not target leakage (identity presence is genuinely available at prediction time, unlike a
  post-hoc label-derived statistic), but it is a strong signal in its own right and a candidate
  feature (`has_identity`) worth flagging explicitly for Phase 2/4 rather than leaving implicit.

Boundaries are at the 60/70/80th percentile of the **time range**, not the 60/70/80th percentile of
row count. **Transaction volume is not uniform over time**: the first 60% of the time range holds
64.5% of rows, while the 10%-wide fold 1 window holds only 9.7% — meaning row density varies
meaningfully across the window and a purely row-count-based split would carve time boundaries
differently than a purely time-based one. Fold 1 also has a visibly elevated fraud rate (4.11% vs
~3.4% elsewhere).

## Phase 2 decisions table

| Decision point | Recommendation | Basis |
|---|---|---|
| Split boundary count/placement | Use ≥3 expanding folds; do not place a boundary inside the 17,191 tied-`DT` rows; treat the 60/70/80% time-quantile boundaries above as reasonable starting points, not final | §2, §8 |
| Row-count vs time-quantile boundary choice | Prefer **time-quantile** (matches the mandatory expanding-window spec in `prd.md` FR2); row-count quantiles would shift boundaries because density is non-uniform | §8 |
| `TransactionID` as a feature | **Ban permanently** | §2 (ρ≈1 with `TransactionDT`) |
| Global-mean imputation | **Do not use** for the `M7`/`M8`/`M9`/`V1–V11`/`D11` drift block; scope imputation to past-only data within each split window | §3 |
| Frequency/categorical encoding | Safe past-scoped encoding for the 14 profiled categoricals (0% OOV observed); `card1/2/3/5` and identity-table categoricals need a dedicated OOV check first | §6 |
| `V`-column feature engineering | Use the 15 null-mask blocks as sampling/grouping units, not raw column-index order | §4 |
| Quantization calibration (Phase 5 handoff) | Heavy-tailed columns (`TransactionAmt`, several `V` columns with skew >100) will need clipping or non-uniform binning; do not calibrate from raw min/max | §5 |
| Candidate feature | Add `has_identity` (join presence) as an explicit feature rather than leaving it implicit in a merge | §7 |
| Fold-level evaluation | Check positive *counts* per fold, not just rates, before finalizing boundaries — fold 2 above has only 1,737 positives | §1, §8 |

## What Phase 1 deliberately did not do

- No persisted transaction↔identity merge (index-level set arithmetic only) — that belongs to Phase 2.
- No fraud-rate-by-category-value table — would bake target statistics into a committed artifact.
- No pairwise/correlation-based `V`-column clustering — Phase 4 defines tiers from model importance;
  null-mask grouping (§4) already captures the cheap structural signal.
- No cardinality/OOV profiling of `card1/2/3/5` or the identity table's categorical columns —
  explicitly flagged above for Phase 2.
- No peak-process-memory (RSS) measurement — no approved tooling for it on this Windows venv
  (`psutil` isn't installed); that measurement belongs to Phase 7's benchmark infrastructure.
