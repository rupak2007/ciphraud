# Phase 8 — Core Research Experiments (living document)

**Status: grid COMPLETE, analysis COMPLETE (2026-09-26).** All 12 grid configurations ran to completion and have final results; all four gates pass for 9 of them and T3 fails for the three 8-bit LR and three 8-bit XGBoost configurations. The Pareto analysis, result-schema and means-vs-raw validation tests, and the prior-art comparison are done (§6.3–§6.5, `src/analysis/phase8_results.py`, `src/analysis/phase8_pareto.py`, `tests/test_phase8_results.py`). What Phase 8 does **not** establish is listed in §11. Nothing below is an estimate of a benchmark value: every number traces to a `results/phase8_research/*/metrics.json` file (or its archived pre-fix copy) and to `configs/phase8/research_grid.yaml`; the tables in §6.3–§6.5 are generated by `python -m src.analysis.phase8_pareto` and are copied from `results/phase8_research/pareto/pareto_tables.md`.

**Headline findings (validation partition, one input for latency — read §7 before quoting any latency):**
1. **Bit-width decides whether encrypted inference is accurate; 8 bits is not enough for either model.** T3 fails at 8 bits for every tier of both models and passes at the highest feasible width (LR 16, XGBoost 14) for every tier.
2. **The cost of accuracy differs by five orders of magnitude between the two models.** LR (no bootstraps) answers one encrypted request in 8.6–30.9 ms; XGBoost needs 2,651–4,099 s (44–68 min) at 14 bits on this CPU. XGBoost is 0.15–0.17 PR-AUC higher (0.522–0.571 vs 0.348–0.422).
3. **More features help accuracy for both models once quantization is adequate** (LR 16 bits: 0.348 → 0.389 → 0.422; XGBoost 14 bits: 0.522 → 0.543 → 0.571) but do **not** help at 8 bits (quantization error dominates and worsens with more features for LR).
4. **XGBoost cost follows tree count, not feature count.** Early stopping gave 358 / 219 / 271 trees for `top_20` / `top_50` / `top_100`, so `top_20` is the most expensive XGBoost tier.
5. **Pareto:** on every cost axis (latency, memory, ciphertext) the frontier of gate-passing configurations is LR 16-bit at three tiers, then XGBoost 14-bit at `top_50` and `top_100`; `xgboost_top20_bits14` is dominated on latency, memory and ciphertext by `xgboost_top50_bits14`, and every 8-bit XGBoost configuration is dominated.
6. **Prior-art divergence:** the ~6 ms XGBoost figure cited in `docs/prd.md` §11 is not reproduced. Measured XGBoost latency is ≥ 155,000× larger; the measured cost of a single programmable bootstrap on this machine is 4–13 ms (§6.4). No explanation of the cited number is asserted.

## 1. Research question

> How do feature count, quantization bit-width, and ML model complexity affect the predictive performance and computational cost of privacy-preserving fraud detection under FHE?

Phase 8 answers it for the two model types built so far (Logistic Regression, XGBoost). The quantized MLP is Phase 9 and is documented separately, in `docs/fhe_mlp.md` (grid complete as of 2026-09-27) — its combined Pareto analysis with the two models on this page lives in `results/phase9_mlp/pareto/` and is not reproduced here.

## 2. Exact grid

12 configurations = 2 models × 3 feature tiers (`top_20`, `top_50`, `top_100`, the committed Phase 4 tiers) × 2 bit-widths **per model**:

| Model | Bit-widths | Why these |
|---|---|---|
| Logistic Regression | 8, 16 | 16 is the highest width that compiles for LR (`docs/fhe_poc.md` §9.1: 18+ fails with `NoParametersFound`); re-confirmed to compile for all three tiers |
| XGBoost | 8, 14 | 16 and 15 are **infeasible** for every tier (`RuntimeError: Function you are trying to compile cannot be compiled` — "this 18-bit value is used as an input to a table lookup … only up to 16-bit table lookups are supported": the tree circuit needs `n_bits + 2` integer bits and Concrete supports table lookups of at most 16 bits); step-down search 16 ✗, 15 ✗, 14 ✓ (all tiers), 12 ✓. 14 is the largest common compilable width |

The bit-widths are therefore **asymmetric by model** — a measured constraint, not a substitution. No configuration was silently relabeled: an infeasible width is recorded as infeasible.

## 3. Methodology

- **Reuse:** the Phase 7 harness (`src/benchmark/harness.py`, `src/benchmark/run.py` loaders) and the Phase 5/6 compile/handoff/validation code, driven by `src/benchmark/phase8_grid.py` and `configs/phase8/research_grid.yaml`. Seed 42.
- **Data boundaries (unchanged from Phases 2–6):** train-only calibration (LR: all 380,815 train rows; XGBoost: 3,000 seeded train rows + each feature's min/max row); validation for every accuracy number; the test partition is never read (`"test_partition_touched": false` in every file). No random k-fold; no tier or model regenerated.
- **Accuracy gates per configuration** (`docs/fhe_poc.md`/`docs/fhe_xgboost.md` definitions): T0 transfer; T3 quantization (clear-quantized vs float, full validation, bars: decision agreement ≥ 0.99 **and** PR-AUC drop ≤ 0.01, both project-chosen); T2 simulation (LR: full validation, exact; XGBoost: 5,000 seeded rows, exact at the integer level); T1 execution — a **separate 2-row stratified correctness sample (1 fraud, 1 legitimate)**, each row executed once with real encrypt → run → decrypt. Four result classes are kept distinct: float, clear-quantized (`fhe="disable"`), simulated, real FHE.
- **Latency:** **5 repeated executions of one fixed representative input** (not 5 independent samples). The input is validation-row position **32,148** (a legitimate transaction; `_stratified_sample_positions(n=1, n_positive=0, seed=42)`), identical for all 12 configurations. One `keygen()` is amortized across the trials; encrypt, run and decrypt are timed separately; compile time is separate; statistic = mean and sample standard deviation (ddof = 1) with all raw trial values retained. This is kept structurally separate from the 2-row correctness sample.
- **Checkpointing:** every real execution (T2 chunks, T1 rows, latency trials) is saved to `data/fhe_handoff/phase8/checkpoints/{label}/` with a fingerprint, so an interrupted run resumes at the next unfinished item; resumed items are spot-checked against a fresh simulation. Metrics and provenance are written only after a configuration completes.
- **Failures:** any exception is recorded in `metrics.json` (`*_failed` status with type, message, traceback); nothing is dropped.

## 5. LR scaler erratum — verified

**What was wrong.** The plaintext LR is `StandardScaler → LogisticRegression`. The handoff stores **raw** feature matrices, but `lr_coef` belong to the model trained on **standardized** features. Before the fix, `src/fhe/poc.py` (Phase 5) and `src/benchmark/run.py` (Phase 7/8) built, calibrated and evaluated the compiled LR on the raw matrices, so it computed `σ(w·x_raw + b)` instead of `σ(w·(x−μ)/s + b)`. T0 (which rebuilds the whole pipeline, scaler included) and T1/T2 (which compare the circuit to the clear-quantized version of the same function) could not see this; T3 did fail, but its failure was attributed to quantization.

**How it was found and confirmed.**
1. *Audit (2026-09-25), numpy only, real Phase 5 handoff:* the raw-input function gives validation PR-AUC 0.0583 / ROC-AUC 0.5846 / decision agreement 0.9615, matching the recorded Phase 5 `n_bits=16` T3 (0.0583 / 0.5836 / 0.9614); the correctly scaled function reproduces the stored reference exactly (max |Δ| = 0).
2. *Fix:* `standardize_features()` (`src/fhe/handoff.py`) applies the scaler client-side, and the compiled LR now only ever sees standardized inputs (`src/fhe/poc.py`, `src/benchmark/run.py`, `src/benchmark/phase8_grid.py`). T0's raw-input reconstruction is unchanged. XGBoost code paths, results and checkpoints are unchanged.
3. *Regression tests (WSL, 55 passed):* a compiled LR built on standardized raw-feature data agrees with the plaintext pipeline; the old raw route does **not** (negative control); the Phase 8 LR runner passes tight T3 tolerances on a synthetic model.
4. *Corrected re-run of all six LR configurations* (same methodology, tolerances and grid; old checkpoints not reused — new fingerprint tag `standardized-input-v2`). Pre-fix results are preserved, byte-identical, in `results/phase8_research/prefix_lr_scaler_bug/` and `data/fhe_handoff/phase8/checkpoints_prefix_lr_scaler_bug/`.

**Old vs corrected** (regenerate: `python -m src.analysis.lr_scaler_fix_comparison`; source: `results/phase8_research/lr_scaler_fix_comparison.{json,md}`):

| `lr_top20_bits16` | 0.9614 | 0.2901 | 0.99969 | 0.00020 | 0.3482 / 0.3484 | PASS |

**Interpretation (verified).** The pre-fix LR "quantization failure" was overwhelmingly the scaler omission: quantized PR-AUC rose from 0.039–0.058 (random-guess floor ≈ 0.035) to 0.25–0.42. What remains after the fix is genuine quantization error: **8 bits still fails T3 for LR at every tier (and worsens with feature count: PR-AUC drop 0.027 at `top_20`, ≈ 0.139 at `top_50` and `top_100`), while 16 bits passes every gate at every tier (agreement ≥ 0.9995, PR-AUC drop ≤ 0.0003).** T0, T1 and T2 passed in all twelve LR runs before and after.

**Committed documents this supersedes (left unmodified, per the Phase 8 constraint on Phase 1–7 artifacts):** the T3 diagnosis in `docs/fhe_poc.md` §8–9 (heavy-tailed min/max quantization as the cause), the statement in `docs/fhe_xgboost.md` §7 and `docs/plan.md` (Phase 5/6 status) that Phase 6 "independently reproduces the Phase 5 LR quantization finding" for LR, and the LR numbers in `results/phase5_fhe_poc/` and `results/phase7_benchmark/` (timings and circuit shape remain valid observations; accuracy numbers do not). The skewed-range observation in `docs/fhe_poc.md` §8 is still a true statement about the data; it was simply never the cause of the LR failure.

### 6.4 Prior-art comparison (`docs/prd.md` §11; `docs/plan.md` Phase 8 exit criterion) — honest divergence

`docs/prd.md` §11 cites an encrypted-XGBoost fraud-detection thesis reporting inference latency "as low as 6 ms" (vs 296 ms for a neural network), and a peer-reviewed LR/XGBoost FHE fraud paper. Neither source document is in this repository and I did not re-read them for this analysis, so their model sizes, tree counts, bit-widths, schemes, libraries, hardware, threading and exact definition of "latency" are **unverified here**. The comparison below is therefore a comparison of numbers, not of experiments.

| | Measured here (this CPU, Concrete-ML 1.9.0, 5 repeated executions of one input) | Cited |
|---|---|---|
| Logistic Regression, 16 bits, 20–100 features | 8.6–30.9 ms | not stated in the PRD |
| XGBoost, 8 bits, 20–100 features (219–358 trees) | 931–1,097 s | ≈ 6 ms |
| XGBoost, 14 bits, 20–100 features (219–358 trees) | 2,651–4,099 s | ≈ 6 ms |

**Divergence: the cited XGBoost figure is not reproduced; the measured XGBoost latency is 1.6 × 10⁵ to 6.8 × 10⁵ times larger.** What the measurements do establish:
- The measurement is internally reproducible: the same `top_50` 8-bit circuit measured ≈ 1,238 s in Phase 6, 1,358.6 s in Phase 7 (2 trials) and 931 s in Phase 8 — the same order of magnitude across three sessions (session-to-session spread of about ± 20% around the mean, larger than the within-run spread for some configurations; §7.1).
- The cost is explained arithmetically by the circuit, not by an anomaly: a Concrete-ML XGBoost circuit for these models has 152,000–384,000 programmable bootstraps, and the measured latency per bootstrap is 4.4–12.7 ms (§6.3). A latency of 6 ms is about **one** bootstrap on this machine.
- The LR latencies (6.5–30.9 ms) are the same order as the cited figure, but LR has no bootstraps at all and is a different model; that coincidence must not be read as agreement.

Candidate explanations for the gap — **none tested here, none asserted**: a much smaller model than ours (fewer or shallower trees), a different FHE scheme or library, a different tree-evaluation strategy, different hardware (more cores, a GPU), a different definition of what the reported latency covers, or a figure obtained without full-precision comparisons. Resolving this would need the cited setup itself. The neural-network figure (296 ms) is compared against the quantized MLP in Phase 9 (`docs/fhe_mlp.md` §7.6): measured MLP latency is 17–245× that figure across the three configurations that reached FHE execution, with the same caveat — the cited setup was not verified. For the final report the defensible statement is: *under Concrete-ML 1.9.0 on a 6-core CPU, XGBoost fraud models with 219–358 trees needed 15–68 minutes per encrypted request; the ~6 ms literature figure was not reproduced.*

## 7. Observations and caveats that affect how numbers may be used

1. **Latency variance is large and not fully explained.** Relative standard deviation (std ÷ mean) across the six XGBoost configurations is 1.2% (`xgboost_top20_bits8`, an overnight run with nothing else running), 22.9% (`top_50` 8 bits), 23.2% (`top_100` 8 bits), 29.1% (`top_50` 14 bits), 28.0% (`top_20` 14 bits) and 22.8% (`top_100` 14 bits). There is no common trial-order pattern: `xgboost_top50_bits8` and `xgboost_top50_bits14` decline over the five trials, `xgboost_top20_bits14` starts high (6,071 s) then settles near 3,400 s, and `xgboost_top100_bits14` *rises* for four trials (2,528 → 4,752 s) before falling. During the first two `xgboost_top50_bits14` trials I ran other work on the same machine (audit reading, document builds, small Windows test runs), and the one very quiet run is the most stable, which is compatible with concurrent activity being one cause; that is a **hypothesis, not verified**, and it does not explain the rising `xgboost_top100_bits14` trials (one candidate not tested: thermal or power-state throttling of the CPU under sustained load). All raw trial values are retained; means and standard deviations are reported over all five; nothing was excluded. The same 8-bit `top_50` circuit also measured 1,238 s (Phase 6), 1,358.6 s (Phase 7, 2 trials) and 931 s (Phase 8) in different sessions. Consequently the latency means for XGBoost should be quoted with their standard deviations and read as ±20–30%.
2. **`fhe_latency.keygen_seconds` is not a real key-generation time in Phase 8.** The accuracy stage already generates keys in the same process, so the latency stage's `keygen()` returns almost immediately (0.0028 s for `xgboost_top50_bits14`). The real cost was measured in the T1 stage: **5.62 s** (`accuracy.gates.t1_correctness.round_trip_timing.keygen_seconds`), and ≈ 2.1–2.2 s in Phase 6 at 8 bits. Cite the T1 value.
3. **`peak_rss_mb` is the whole process high-water mark** (load + compile + full-validation gates + trials), not inference-only memory.
4. **Resumed items.** `xgboost_top50_bits14` was interrupted once (a WSL/session kill during T1, exit code 4, no Python error) and resumed from verified checkpoints; the T2 chunks and part of the run therefore come from different sessions. `T2.simulate_seconds_per_row` is NaN there because every chunk was reused.
5. **Recorded timings under-count real elapsed time by roughly 5–11% (measured, cause unverified).** Every latency and compile time is a `time.perf_counter()` interval inside WSL2. On 2026-09-26, while `xgboost_top100_bits14` was computing at ≈ 600% CPU, a sleep-only probe measured WSL `perf_counter`/monotonic advancing **180.003 s** while WSL's realtime clock advanced **201.505 s** and the Windows host wall clock advanced ≈ 200.3 s: the WSL monotonic clock ran ≈ 10–11% slow relative to real time. This matches an otherwise unexplained gap in the checkpoint data: for each real execution, the host-clock interval between consecutive checkpoint saves exceeds the recorded `total_seconds` by a steady ≈ 5–11% (e.g. `xgboost_top20_bits8`: +6.9…+8.0%; `xgboost_top50_bits14`: +4.5…+6.0%; `xgboost_top20_bits14`: +9.4…+11%). Recorded means/standard deviations are therefore reported **as recorded** (VM monotonic time) and must be read as a lower bound on real wall-clock latency by up to ≈ 11%; the checkpoint file modification times (host clock) are an independent second time source retained in the raw data. The dilation factor may differ between sessions and load levels, so it can also add a few percent of apparent run-to-run variance. Not verified: why the monotonic clock lags (candidates: WSL2/Hyper-V timekeeping under sustained full-core load).
6. **`xgboost_top20_bits14` was interrupted once and resumed.** Latency trials 1–2 (index 0–1) were saved on 2026-09-25/26 (23:28 and 00:44 IST); the checkpoint metadata was rewritten at 02:47 IST, showing a re-launch, after which trials 3–5 completed (saved 03:50, 04:53, 05:55). The trial in flight when the process stopped (the third) was lost and re-run; how the re-launch happened is not recorded (Unknown). So trials 1–2 and 3–5 come from two separate processes.
7. **All accuracy numbers are validation numbers**, and validation data also selected the early-stopping tree count, the decision thresholds and the tiers; no test-partition evaluation has been performed.
8. **`xgboost_top100_bits14` was interrupted by a deliberate pause and resumed.** Latency trials 1–3 were saved on 2026-09-26 (02:56, 04:01, 05:12 UTC) by one process; the run was then stopped on purpose (SIGTERM, PC shut down) with trial 4 about 40 minutes in, and trials 4–5 were computed by a fresh process after WSL rebooted (finished 13:29 UTC). The unsaved trial was lost and re-run; all saved trials, the two T1 rows and the T2 chunks were reused unchanged from the checkpoints. The key generation in trials 4–5 is a new key (a new process), so the five trials come from two processes/keys, as for `xgboost_top20_bits14` (§7.6).
9. **Wall-clock time per config.** Because trials are checkpointed only on completion, an interruption costs the in-flight trial (up to ≈ 70 min here). Total interruptions during the grid: `xgboost_top50_bits14` (killed in T1), `xgboost_top20_bits14` (WSL restart), and the pause above; none changed a recorded value.

## 11. Phase 8 exit criteria and what Phase 8 does not establish

`docs/plan.md` Phase 8 exit criteria: **full grid executed for LR and XGBoost** — yes, 12 of 12, ≥ 5 trials each; **Pareto frontiers generated** — yes (§6.3, `results/phase8_research/pareto/`); **prior-art comparison written up** — yes, as an honest divergence (§6.4); **tests** (results-schema validation; means match raw trials) — yes, `tests/test_phase8_results.py`.

Limits that a reader of the results must keep (none of these were worked around):
- **Validation only.** No number is a test-partition number; validation data also selected trees, thresholds and tiers.
- **One input for latency.** Latency is 5 repeated executions of one legitimate-class row, not a distribution over inputs, and XGBoost latency may depend on the input path through the trees (not measured). The 2-row correctness sample is separate.
- **One machine, one library version, one clock.** VM monotonic-clock timings under-count real elapsed time by ≈ 5–11% (§7.5); no GPU, no multi-machine or cloud run.
- **Variance.** XGBoost latency has 23–29% relative standard deviation in five of six configurations; the tier ordering by latency is not statistically established (§6.3).
- **Bit-widths are model-specific** (LR 8/16, XGBoost 8/14) because higher widths do not compile (§2); the two models are compared at each one's highest feasible width, not at equal precision. Only two widths per model were run, so the accuracy-vs-bit-width curve between 8 and the top width is unmeasured.
- **The T3 bars (agreement ≥ 0.99, PR-AUC drop ≤ 0.01) are project-chosen**, not derived from a business cost model; no threshold/cost-sensitive analysis was done in Phase 8.
- **No security or timing-side-channel measurement**; this phase measures cost and quantization accuracy only.

Not part of this project stage: the client/server implementation (Phase 10), test-partition evaluation, and any GPU or cloud FHE experiment. The quantized MLP (Phase 9) is complete and documented separately in `docs/fhe_mlp.md`; it is not part of *this* Phase 8 document, but is no longer "not started."
